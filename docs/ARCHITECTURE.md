## 分工与硬件

电脑浏览器 → 本机 Python 服务 → ESP32（HTTP 管理 + UDP 速度心跳）→ USART1 → STM32 HAL App → CAN1 → C610/M2006。
主机服务只在 `127.0.0.1:18765` 监听；令牌存于本地配置，浏览器不持有 ESP32 令牌。

| 项目 | V1 配置 |
|---|---|
| STM32 | STM32F103C8T6，64 KiB Flash / 20 KiB RAM |
| 时钟 | 原板 8 MHz HSE → 72 MHz SYSCLK；APB1 36 MHz |
| CAN | PA11 RX / PA12 TX，1 Mbit/s，Prescaler 6，BS1 3TQ，BS2 2TQ |
| 电机 | ID 0x201 右轮反向，0x202 左轮正向；反馈 FIFO0 轮询 |
| 电流发送 | 标准帧 0x200，右轮和左轮两个 int16 大端；通道 3/4 固定零 |
| ESP32 串口 | GPIO17 TX → PA10 RX，GPIO16 RX ← PA9 TX，GND 共地，115200 8N1 |
| SWD | SWDIO → PA13，SWCLK → PA14，GND 共地 |

这些映射由旧工程取得，新板上的 CAN 收发器、终端电阻、电机 ID 和轮子方向仍需实物确认。

## Flash 布局

| 区域 | 地址 | 容量 |
|---|---|---|
| Bootloader | 0x08000000 | 16 KiB |
| App | 0x08004000 | 46 KiB |
| 有效记录 | 0x0800F800 | 1 KiB |
| 保留参数 | 0x0800FC00 | 1 KiB |

App 升级仍使用旧工程经验证的“先撤销记录 → 擦写 App → 全体 CRC/向量校验 → 最后提交有效记录”。
新 App 启用独立看门狗（LSI 典型频率下约 1 秒，实际随 LSI 偏差变化），新 Bootloader 在接收循环和逐页擦除时接续喂狗。
App 身份为 `SC01`，当前源码固件版本为 125（以 `drive.h` 中 `DRIVE_VERSION` 为准）；Bootloader 为兼容已有协议继续使用 `M2B2`，网关身份 `SG01`。
OTA 发送端等待新 App 身份，再 QUERY 核对版本，不能只凭 HTTP 请求成功判断安装完成。

## 运动状态与限制

- `DISARMED=0`：目标、电流与积分均为零。
- `ARMED=1`：收到明确 ARM 后允许速度控制；ARM 要求两轮反馈有效且静止。
- `FAULT=2`：故障锁存，普通速度和 ARM 均不能恢复；CLEAR 需反馈有效且静止，随后仍为 DISARMED。
- `UPDATING=3`：进入 Bootloader 前的短暂状态，不接受运动。

故障码：0 无故障；1 控制超时；2 反馈超时；3 CAN 错误；4 UART 接收/发送错误。
控制周期 10 ms，控制消息有效期 300 ms，反馈有效期 100 ms。
同一 ARM 会话中只接受严格递增的 32 位命令序号；重复/迟到/错误会话不刷新时间。
界面每 100 ms 发一次当前目标；主机与 ESP32 不替断线页面自动续发。
当前 v125 使用按轮/方向选择的速度 PI：右轮反转 P=0.45，其余 P=0.30；稳态 I=0.010/控制周期，5–10 rpm 尚未起转阶段 I=0.030/控制周期，D=0。误差使用电机轴 rpm，标称控制周期 10 ms。启动积分增量限幅6、启动输出限幅450，通用积分限幅1200、输出限幅2000；达到同方向轮速1 rpm后削减过大的积分，释放输出上限一般150、右轮低速反转180。停转100 ms可重新进入启动保护。具体触发边界以 `drive.c` 为准，参数演进与未解决问题见 [PID 调试记录](PID_TUNING.md)。未加入固定死区补偿或速度前馈。
速度反馈由 C610 的 8192 刻度编码器角度展开累计位置，再以约 30 ms 差分窗口计算；此速度实际参与闭环与遥测，并非只平滑图表。窗口预热或反馈间隔过长时回退原始 RPM；CAN 新鲜度仍取真实收帧时间。模块见 `Core/Src/angle_speed.c`，已加入 MDK 与 EIDE 工程。v124起重新加入起步诊断：冻结最初256个控制周期，仅在禁止驱动/故障且零输出时导出；详见验收记录。
架空 5/10 rpm 的实测迭代见 `ACCEPTANCE.md`；不能由架空结果推断落地载荷、全速度范围或长期可靠性。低速起步时间仍可能因两轮阻力不同而不同。
速度单位：协议为电机轴 rpm，减速比 36，页面除以 36 显示轮速；第一版不估算里程或车体绝对速度。

## 新控制协议

沿用 `A5 5A / version / type / seq16 / length16 / payload / CRC32`，多字节字段小端。

`type=0x40`，固定 16 字节：

| 偏移 | 类型 | 内容 |
|---|---|---|
| 0 | u8 | 操作 0 DISARM / 1 ARM / 2 SPEED / 3 CLEAR |
| 1–3 | 3 字节 | 必须零 |
| 4 | u32 | 非零 ARM 会话，SPEED 必须匹配 |
| 8 | u32 | 命令递增序号 |
| 12 | i16 | 左轮电机轴目标 rpm |
| 14 | i16 | 右轮电机轴目标 rpm |

应答 `0x71`，16 字节：0 结果（0 成功、1 参数错、2 状态错、3 反馈无效、4 序号错）；1 状态；2 故障；3 保留；4 会话；8 最后序号；12–15 保留。

遥测 `0x10`，固定 40 字节，100 ms 一次：

| 偏移 | 内容 |
|---|---|
| 0/4 | u32 启动毫秒 / 固件版本 |
| 8/9/10/11 | u8 状态 / 故障 / 双轮反馈掩码（bit0 左、bit1 右）/ 保留 |
| 12/14 | i16 左/右目标转速 |
| 16/18 | i16 左/右实际转速 |
| 20/22 | i16 左/右输出电流原始命令 |
| 24/26 | i16 左/右反馈电流原始量 |
| 28/32/36 | u32 会话 / 序号 / 串口错误计数 |

旧 M1 的 `tests/legacy/car_protocol.py` 中 Telemetry 样本仅用于历史帧测试，**不得用于解析 V1 运动遥测**；V1 电脑端使用 ESP32 `/telemetry` JSON。

## ESP32 HTTP

GET `/status`：缓存完整性和最近 STM32 身份；GET `/telemetry`：运动快照和年龄，500 ms 未更新时 valid=false。
POST `/control`：Bearer 认证，正文为上面的 16 字节；等待 STM32 应答，拒绝时返回 409，无应答为 504。
POST `/cache`：Bearer 认证，上传元数据+App；POST `/install`：认证、32 位十六进制字符请求 ID 和 `<size,crc,version>` 三个 u32。
安装与控制共享串口互斥锁。HTTP 服务串行处理请求；安装期间不处理控制，STM32 入口门槛防止带着运动状态进入更新。

## 速度心跳传输（2026-09-18）

ARM、DISARM、CLEAR、遥测和 OTA 使用 HTTP，控制与遥测分开持久连接；ESP32 关闭 Wi-Fi 省电并在响应上启用 TCP_NODELAY。
速度心跳由网页按约 100 ms 周期生成，经本机服务向 ESP32 UDP 3232 端口发送一次，不等待无线应答，不重传旧目标。
固定 52 字节：`SCU1`（4）+ 本机令牌 ASCII（32）+ 原 16 字节控制载荷；只允许 SPEED=2，非零会话与序号，目标范围 ±720 电机轴 rpm。
ESP32 有界读取并保留同会话最新序号，UART 占用时直接丢弃；STM32 原有会话、递增序号、300 ms 截止时间校验保持不变。
UDP API 的 `sent_unconfirmed` 只表示本机发送，不能当作 STM32 接受；实际状态及序号以遥测为准。
HTTP 控制 ACK 使用高半区串口 seq16，UDP 使用低半区，避免混淆应答；业务控制仍用原有 uint32 序号。
单次遥测读取超时为 200 ms，失败不改变最后样本时间；累计设备年龄或本机样本年龄达到 500 ms 后停止网页心跳。
电脑可用同路由器 5 GHz/网线，ESP32 使用 2.4 GHz。任何链路长时间中断仍应触发故障，不保证无线绝不丢包。
