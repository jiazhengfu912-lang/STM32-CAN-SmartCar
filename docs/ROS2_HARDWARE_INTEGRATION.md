# ROS 2 上层与 STM32 底层的集成边界

本文依据 2026-10-18 仓库源码核对接口。本轮把仿真、SLAM 和 Nav2 工程纳入 `ros2_ws`；**尚未实现 ROS 2 到实车的驱动桥，未连接设备、烧录固件或执行实车运动。**在 Gazebo 中导航成功不等于实车导航通过。

当前 STM32 源码版本为 **131**，见 [drive.h](../firmware/stm32_app/Core/Inc/drive.h)。[ICM 升级记录](ICM42688_UPGRADE.md)明确：最近记录的设备运行版本为 127，v131 未安装，主控供电/通信恢复、ICM 真实采样、安装方向与导航精度仍待验证。这些是历史记录状态，不是本轮在线探测结果。

## 1. 三层职责与本轮交付

| 层级 | 运行位置 | 负责的功能 | 本轮状态 |
|---|---|---|---|
| ROS 2 上层 | Ubuntu 22.04 / Humble 主机 | C1 扫描处理、二维 SLAM、AMCL 定位、Nav2 路径规划/跟踪/恢复、RViz | `ros2_ws` 提供 Gazebo Fortress 仿真工程 |
| 通信与所有权 | 主机桥接程序、现有本地控制台、ESP32 | 指令新鲜度、控制权、认证、协议转换、遥测传输 | 现有网页链路存在；ROS 硬件桥待实现 |
| 实时控制 | STM32 / CAN / C610 / M2006 | 双轮速度 PI、电流输出、编码器反馈、IMU、超时与故障锁存 | 保留现有固件；本轮不修改 PI 或硬件协议 |

以后实车的建议链路为：

```text
Nav2 → 速度平滑/导航保护 → ROS 硬件桥（待实现）
     → 同一个本机控制台的控制权入口 → ESP32 → USART1 → STM32 → CAN 电机

STM32 编码器/IMU → ESP32 遥测 → 本机控制台 → ROS 硬件桥（待实现）
     → /odom、必要的 /imu/data、/diagnostics、odom → base_footprint

真实 C1 的 ROS 驱动（待接入）→ /scan → SLAM 或 AMCL/Nav2
```

SLAM、AMCL 和 Nav2 继续运行在 Ubuntu，不能把这些 ROS 包编进 STM32 固件。STM32 已有的“相对坐标单目标导航”是另一套简单外环，不包含障碍感知和路径搜索，不能与 Nav2 同时控制轮速。

当前 [navigation.launch.py](../ros2_ws/src/smartcar_nav2/launch/navigation.launch.py)会启动 Gazebo，并使用 `/sim/scan`、`/sim/odom`、`/clock`；[navigation_gate.py](../ros2_ws/src/smartcar_nav2/scripts/navigation_gate.py)也检查仿真接口。**这不是实车启动文件，不能仅把速度话题接到硬件便认为已完成适配。**

## 2. 现有接口与准确单位

接口依据：[desktop/server.py](../desktop/server.py)、[ESP32 main.cpp](../firmware/esp32_gateway/src/main.cpp)、[control_datagram.c](../firmware/esp32_gateway/control_datagram.c)、[smartcar.c](../firmware/stm32_app/Core/Src/smartcar.c)。

### 推荐复用本机控制台

现有 Python 控制台仅监听 `127.0.0.1:18765`。未来 ROS 桥与网页必须使用**同一个控制台实例**，复用其 `owner`、ARM 会话和递增序号。另开一个控制台实例，或 ROS 桥绕过控制台直接向 ESP32 发运动命令，都不会自动共享网页层的所有权。

| 本机接口 | 当前含义 |
|---|---|
| `GET /api/state` | 返回 `telemetry`、`csrf`、升级状态和已接受的导航配置缓存；这是读取，不发送心跳 |
| `POST /api/control` | JSON `{op, owner, at, left, right}`；`at` 为当前 Unix 毫秒时间，接受窗口为 250 ms；`left/right` 必须为整数电机轴 rpm，范围 ±720 |
| `X-Console-Token` | POST 必须携带当前控制台 `csrf` 值；它与 ESP32 的 Bearer 令牌不同 |
| `POST /api/navigation` | STM32 内置直行/转角/相对坐标导航和配置接口；不是 Nav2 action 的转发接口 |

`owner` 是控制客户端身份字符串；使能时控制台创建非零 `session`，维护 `uint32` 递增 `sequence`。不能把这些字段当作可以由不同客户端各自随意拼接的共享控制权。

### ESP32 到 STM32 的已有协议

ESP32 HTTP `POST /control` 使用 `Authorization: Bearer <本机配置令牌>`，正文为 16 字节。速度心跳走 UDP 3232：固定 **52 字节**，依次为 `SCU1`、32 字节 ASCII 令牌、16 字节控制载荷。UDP 只接受操作 2 或 4，每次仅转发本次收到的数据包；网关不会替断线控制端持续发送运动指令。令牌不进入源码、日志或图表。

16 字节载荷为小端 `u8 op, 3 字节零, u32 session, u32 sequence, i16 left, i16 right`，对应 Python `'<B3xIIhh'`：

| op | 操作 | 约束 |
|---|---|---|
| 0 | DISARM，停止并禁止驱动 | 清零目标、电流和积分，撤销会话；已有故障不会因此清除 |
| 1 | ARM，使能 | 禁止驱动状态、双轮反馈新鲜且接近静止、非零新会话、零目标 |
| 2 | SPEED，左右轮目标 | 当前 ARM 会话、严格递增非零序号；被接受后取消 MCU 内置导航 |
| 3 | CLEAR，清故障 | 当前为故障状态、双轮反馈新鲜且接近静止、零目标；随后仍是禁止驱动 |
| 4 | MCU 内置导航心跳 | 左右目标必须零，且内置导航正在运行；只续租已有动作，**不用于 Nav2 速度控制** |

普通控制经 USART1 的帧类型为 `0x40`，应答为 `0x71`；帧封装使用仓库现有 `A5 5A / version / type / seq16 / length16 / payload / CRC32`。`seq16` 是传输帧序号，`sequence` 是业务控制序号，不应混用。参见 [car_protocol.h](../protocol/car_protocol.h)、[car_protocol.c](../protocol/car_protocol.c)。不要另行发明一套串口帧、CAN 速度帧或认证机制。

UDP API 返回 `sent_unconfirmed` 仅表示本机已发送，不能当成 STM32 接受；必须用真实遥测中的状态、会话、序号和目标核对。

### 左右轮与 CAN 极性

软件统一采用左轮索引 0、右轮索引 1；**归一化后双轮正 rpm 表示约定的同向前进**，实物轮向仍需要架空确认。

- C610 反馈 ID `0x202` 对应左轮，`0x201` 对应右轮。
- STM32 在接收右轮反馈时取反，在发送右轮电流时再次映射回硬件极性。
- 电流命令是 CAN `0x200` 标准 8 字节帧：前两个 `int16` 大端分别是右轮、左轮；其余两路零。它是电流控制命令，不是左右轮 rpm 帧。
- 因此 ROS 桥使用 `/api/control` 的 `left/right` 时**不能再额外把右轮取反**。

全部控制目标和 `rpm_left/rpm_right` 遥测均为**电机轴 rpm**。36:1 减速后才得到车轮 rpm；电流字段仍是电调原始量，未经电流标定不能直接标为安培。

## 3. Twist 到轮速，以及实车限速

对于差速底盘，`linear.x=v` 单位 m/s，`angular.z=ω` 单位 rad/s，左转 `ω>0`。轮距为 `b`、左右有效轮径为 `dL/dR`、减速比为 `G=36`：

```text
vL = v - ω × b / 2
vR = v + ω × b / 2
motor_rpm_L = vL × 60 × G / (π × dL)
motor_rpm_R = vR × 60 × G / (π × dR)
```

未来桥应拒绝非有限数值和不支持的横移/其他轴指令。超过轮速边界时需要对左右轮**共同缩放**以保持曲率，并把真实执行能力反映到 Nav2 参数；不能仅在最末端长期截断速度、让上层仍按更快的车辆规划。

[仿真参数](../ros2_ws/src/smartcar_sim/config/robot_parameters.json)中轮径为用户确认的 65 mm，轮宽 27 mm，轮距按模型为 252 mm。**252 mm 尚不能替代落地有效轮距测量，65 mm 名义轮径也需通过负载滚动距离标定。**下面仅按这些数值作单位换算，不是实测最高速度：

| 项目 | 理论换算 |
|---|---|
| 现有硬件边界 ±720 电机轴 rpm | ±20 车轮 rpm |
| 65 mm 轮径、20 轮 rpm 直行 | 约 **0.0681 m/s** |
| 仿真直行 0.30 m/s | 约 **3173 电机轴 rpm**，明显超出现有 ±720 限制 |
| 252 mm 轮距，双轮以相反方向各 20 轮 rpm 原地转动 | 约 **0.540 rad/s**；有平移时允许角速度更低 |
| 仿真 RPP 原地转向 0.60 rad/s | 按上述几何需要约 800 电机轴 rpm，同样超出现有边界 |

当前 [nav2.yaml](../ros2_ws/src/smartcar_nav2/config/nav2.yaml)的巡航速度、速度平滑器、转向/恢复速度、最小接近速度与加减速均是仿真配置。未来需要单独的实车参数文件，根据实际低速起步、停止距离、控制延迟和轮胎表现选定参数。不能为了复用仿真 0.30 m/s 而放宽底层速度限制或取消超时保护。

## 4. 遥测、里程计与 TF

### 现在有哪些真实协议字段

40 字节运动遥测通过 ESP32 `GET /telemetry` 解码为 JSON；控制台 `GET /api/state` 将其放在 `telemetry` 下：

- `valid`、`age_ms`、`uptime_ms`、`version`；
- `state`、`fault`、`feedback_mask`（bit0 左轮，bit1 右轮）；
- `target_left/right`、`rpm_left/right`、`output_left/right`、`current_left/right`；
- `session`、`sequence`、`io_errors`。

常规运动遥测为 10 Hz。网关缓存年龄达到 500 ms 时 `valid=false`；控制台另计算本机样本年龄，读取失败不会刷新最后样本时间。**500 ms 是遥测显示/传输有效期，不是授权延长底层 300 ms 控制期限。**

另有独立的 112 字节 `0x12` IMU/相对定位消息，网关提供 `imu_wire`、`imu_age_ms` 和 `imu_transport_valid`，控制台通过 [imu_protocol.py](../desktop/imu_protocol.py)解码为 `telemetry.imu`。可用字段包括：

- `roll_rad/pitch_rad/yaw_rad`、`gyro_z_rad_s`，以及传感器坐标系的原始加速度/角速度计数；
- `x_m/y_m/heading_rad`：STM32 编码器增量与陀螺仪融合得到的**相对原点**位置；
- `valid/attitude_valid/position_valid/discontinuous/configured/axes_confirmed`、校准状态、动作模式和结果；
- 发送时刻 `uptime_ms`、采样时刻 `sample_ms`、采样 `sequence`、`origin_id`、固件版本、传感器身份；
- I²C 错误/超时、采样缺口、控制间隔、UART 丢帧等诊断。

默认 10 Hz，诊断模式固件可产生 50 Hz 消息；**现有 HTTP 轮询约 10 Hz，并不因此获得 50 Hz 连续原始流**。时间戳是 MCU 接收/发送毫秒时刻，不能直接当 Unix/ROS 时间。40 字节遥测不包含累计编码器计数；112 字节消息也没有暴露每轮累计计数。

MCU 里程计实现见 [navigation.c](../firmware/stm32_app/Core/Src/navigation.c)：角度展开累计值按 8192 刻度和减速比换算轮距离，用陀螺仪/轮差增量融合更新 `x/y/heading`。上电不设置几何参数；需配置轮径轮距、确认轴向、校准、停稳设原点后才可标记位置有效。丢样、IMU重置、编码器展开不连续等会使定位失效；恢复通信不会自动恢复旧原点。

### ROS 侧待实现的明确责任

| TF / 数据 | 唯一责任方 |
|---|---|
| `map → odom` | 建图时 SLAM Toolbox；已知地图导航时 AMCL；两者不能同时发布同一变换 |
| `odom → base_footprint` | 经验证的硬件里程计桥，或唯一选定的融合节点 |
| `base_footprint → base_link → laser_frame/imu_link` | 实测外参对应的机器人模型/静态变换 |
| `/odom` | 与 `odom → base_footprint` 同一估计源，含实际时间、速度和合理协方差 |
| `/scan` | 真实 C1 驱动，核对 frame、时间戳、角度方向与量程 |

首条可评估路线是把有效的 MCU `x/y/heading` 映射为局部 `odom`，用归一化轮速推导车体速度；应明确它已经融合过陀螺仪，避免再把同一信息当独立测量重复融合。另一条路线是从轮速积分得到轮式里程计，但现有约 10 Hz 速度和 Wi-Fi 延迟/缺测会丢失信息，不能把它宣传为高精度编码器里程计。若后续要上送累计编码器及设备采样时间，必须通过新协议版本、兼容性测试和实物验收实现，不得把未存在的字段写进解析器。

桥还需要处理重复样本、设备复位、`uint32` 时间回绕、传输年龄、原点代次改变和无效标志。不得给旧样本套上不断更新的时间戳，也不得在 `position_valid=false` 时继续发布看似正常的连续定位。原点/时间发生不连续时应暂停导航并显式重新初始化；不能让 TF 静默跳变后继续旧目标。

实车使用 `use_sim_time=false`，不能依赖 Gazebo `/clock`。当前仿真 URDF 的外参、惯量、摩擦、质量、相机 FOV 中仍有估算项；里程计原点、轮轴中心、雷达扫描平面和 IMU 安装轴向需实测匹配。仿真办公室地图也不代表真实房间地图，需要用真实 C1 数据重新建图。

## 5. 控制权切换与停机语义

未来 ROS 桥应默认禁止驱动，启动 ROS 或发布一个 Twist 不应隐式 ARM。控制台现有互斥锁及 `owner` 检查提供入口，但仍需实现 ROS 生命周期、明确的使能/禁止驱动操作、来源仲裁与状态显示。

建议切换流程：取消原控制源任务 → 明确 DISARM → 读回状态与新鲜双轮反馈、确认停稳 → 释放原所有者 → 人工授权新的 ROS 或网页所有者 ARM → 仅接受当前来源的新鲜命令。ROS 和网页不得同时各自产生 ARM 会话和持续速度命令；OTA 时必须先禁止驱动。

新桥必须独立检查上游命令年龄、遥测年龄、状态/故障、控制权和感知/定位状态。通信线程、遥测读取线程与命令发送应有界，不允许旧运动命令排队后执行。只在当前控制源仍有效时发送新鲜速度指令；**上游节点失联后不得不断重发最后一条非零速度**。超时后应尽快请求停止并禁止驱动，保留 MCU 最终超时兜底，不能无条件恢复会话、自动 CLEAR/ARM 或重发旧导航目标。

源码现有底层保护：

- 双轮 PI 调度周期约 10 ms；指令期限 300 ms；任一轮反馈期限 100 ms。
- 已过期会话即使在周期检查前收到迟到命令，也不能续租；重复/迟到/错误会话不刷新期限。
- `FAULT` 锁存故障并清零输出；清故障后仍需显式使能。
- MCU 内置导航另要求约 50 ms 内的新鲜传感器、定位连续性等；普通速度控制不会自动获得这些内置导航检查，未来 ROS 桥必须负责其所依赖的传感器/定位失效处理。
- DISARM/故障时为**零电流滑停**，不是机械抱闸。软件取消 Nav2、软件禁止驱动与独立硬件断电急停是不同层次，停止距离必须实测。

状态枚举：`DISARMED=0`、`ARMED=1`、`FAULT=2`、`UPDATING=3`。当前故障枚举另含 `FAULT_IMU=5`；详见 [drive.h](../firmware/stm32_app/Core/Inc/drive.h)。不因 ROS 集成而调整 PI 增益、改弱故障门槛或让网关代发心跳。

## 6. 分阶段验收与尚未完成事项

后续实车接入应按以下阶段，每一阶段均保留成功、失败与缺测：

1. **硬件恢复与只读确认**：先复核既有供电/主控问题、真实固件版本、ESP32 协议兼容、双轮反馈、ICM 身份/采样和 C1 原始扫描。未解决时不开展运动。
2. **桥接离线测试**：以仓库真实字段构造明确标注的测试样本；验证单位/极性、共同限幅、认证与所有权、旧包/重复包/会话错、暂停/失联/复位/时钟回绕、无效定位、默认禁止驱动和不能自动恢复。替身通过不等于硬件通过。
3. **只读 ROS 驱动**：先输出诊断、有效的 `/scan` 和里程计，核对唯一 TF 发布者、坐标方向、时间同步、静止漂移和外参；保持驱动禁止。
4. **架空低速单轮/双轮**：人工明确使能后确认前后/左右转符号，测指令与真实轮速、取消、DISARM、上游断流、Wi-Fi/UART/CAN 失联、故障锁存/恢复和所有权切换。保留原限速/超时。
5. **落地里程计标定**：独立卷尺/地面坐标与角度参照测轮径、有效轮距、低速起步、转向、停止距离与时间；先验证直行与转角，再决定实车 Nav2 参数。内部估计不能用来证明自身精度。
6. **真实二维建图和单目标导航**：确认 C1 障碍检测、真实地图/AMCL、低速路径跟踪和到达停止；然后验证临时障碍、无法通行、恢复/取消、再次发目标。
7. **多目标与持续运行**：记录完整路线、到点顺序、失败终止、控制源退出与恢复，以及真实网络/供电/负载条件；不能用最优一次代替整体结论。

本轮未实现：实车 ROS bridge、硬件启动文件与独立 Nav2 参数、C1 实车驱动接入、ROS 时间/设备时间同步、硬件里程计与 TF 发布、实车控制权 UI/仲裁服务，以及上述实物验收。源码已经有相关协议字段，不表示这些 ROS 功能已经接通。

每轮按 [ACCEPTANCE_WORKFLOW.md](ACCEPTANCE_WORKFLOW.md) 保存原始 CSV/JSON、SHA256、逐点 PNG/SVG，并把波形直接嵌入 [ACCEPTANCE.md](ACCEPTANCE.md)。图旁标明 PI 前后（未改也写明）、算法、版本、真实工况、异常和缺测。离线仿真波形与真实传感器波形必须明确区分；本说明不会生成或补造未发生的硬件数据。
