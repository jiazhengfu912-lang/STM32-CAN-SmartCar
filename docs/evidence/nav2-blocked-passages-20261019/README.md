# 双通道封堵后遗忘障碍、反复选路的修复

日期：2026-10-19，Asia/Shanghai。仅ROS/Gazebo仿真，未连接硬件。本轮接续同日“全局规划转弯空间”修改，保留其半径0.35m圆形全局轮廓；本轮不再调整轮廓或速度。本轮之前已有的全部未提交修改、AGENTS与HANDOFF均保留，未提交、推送或合并。

## 用户现场与根因

用户在Gazebo摆放一个半径0.5m球体和一个1×1×1m方块，封堵上方两房间通向中央走廊的两个出口，再通过RViz发目标。只读保存的现场日志显示：目标(1.03,-2.92)，规划失败后**6次清空整个全局代价地图**，随后客户端取消目标。不能把用户的取消写成导航自行ABORTED。

现场球体中心约(-2.9082,0.2833,0.5)，方块中心约(3.0925,0.8227,0.5)。`user_session/`保留截图、原世界位姿、Gazebo生成的完整世界、ROS话题清单、导航/规划/控制日志及哈希。只读检查了当前BT路径；原单目标树来自本包，原连续多目标树来自系统默认配置。没有关闭、重启、发目标或清理用户会话中的地图/障碍。

原BT在规划失败时调用`global_costmap/clear_entirely_global_costmap`，控制失败时清空局部图，外层恢复又会清空两图。**不只是局部清理问题**：全局清空会抹去雷达曾经看到、但当前被墙/柜子遮挡的障碍。静态地图本来没有这些新放物体，因此清空后又出现似乎可通行的旧路线。内层清图后短暂重规划成功，还会让失败迟迟不能到达外层有限恢复预算。

Humble官方实现依据：[ClearCostmapService::clearEntirely调用resetLayers](https://github.com/ros-navigation/navigation2/blob/humble/nav2_costmap_2d/src/clear_costmap_service.cpp)、[ObstacleLayer::reset清空图层，raytraceFreespace按新射线清除空闲空间](https://github.com/ros-navigation/navigation2/blob/humble/nav2_costmap_2d/plugins/obstacle_layer.cpp)。本轮不是依据截图颜色猜测根因，另有下面的实际全局图数据对照。

## 修改及边界

- 单目标与连续多目标BT都去掉自动整图清空及内层清图重试；规划/跟踪失败统一进入外层最多4次恢复预算，仍是等待、带碰撞检查的转向、等待、短距离后退。之后返回失败并停车。
- 启动器显式设置两种默认行为树，防止`NavigateThroughPoses`继续使用系统内的旧清图树。`FollowWaypoints`逐个调用单目标，使用同一单目标策略；本轮没有声称任意GUI队列通过。
- 全局/局部扫描的`marking`、`clearing`继续开启，没有关闭射线清障，没有增加旧扫描缓存时间。未看到的远处旧障碍保留；移走后重新被雷达观察到的空闲区域可正常清除。局部滚动窗口照常移动，不把它当成全局障碍记忆。
- 原全局圆形轮廓、局部矩形、NavFn A*、RPP、速度、保护节点、控制器失败/进展期限均未改。地图服务仍可由用户显式调用，生命周期/进程重启也会重新初始化地图；禁止的是自动恢复反复清空整图。
- 仍可探索尚未看到的另一个出口；确认所有出口被堵后才应失败。没有让小车预先读取Gazebo障碍真值用于规划，也没有给规划器注入障碍格。

新增`bt_xml`、`through_poses_bt_xml`启动参数用于明确选择树和复核旧版本。新回归测试检查两种树都不自动清图、规划/跟踪共用有界预算，以及正常扫描清障仍开启。

## 实际仿真与全部尝试

隔离测试使用同一办公室世界、office_01地图，初始世界/AMCL位姿(-2.99,1.91,0)，目标map(1.03,-2.92,0)。按用户现场坐标加入两个相同几何的障碍，测试中设为静态，保证障碍一直在那里；用户原模型是动态模型，原场景未改。单目标封堵阶段只发一个目标，机器人通过真实扫描逐渐发现另一处堵塞。

“障碍记忆”CSV逐帧统计每个障碍中心±0.7m范围内、静态底图原本空闲而全局图现为100的致命格。排除底图已有墙格；仍可能有AMCL/栅格误差导致的墙边格，**格数不是物体尺寸或准确分割结果**。原始完整地图和扫描均保留，可重新分析。

### 停车采集修正

原验收在动作结束后固定采集3墙钟秒，丢开头1秒后要求所有剩余样本静止。低实时率仿真中，3墙钟秒不足以覆盖完整物理减速；例如`after_two_doors_03`最后odom角速度仍约0.065rad/s，未到阈值，记录真实保留。

最终验收改为最多等待15墙钟秒寻找**连续至少1秒、至少10个新鲜样本**，仍要求|vx|<0.02m/s、|wz|<0.03rad/s、窗口位移<0.02m，且新鲜门控速度命令为零。增加的是采集等待，不是控制/失联超时；没有降低静止阈值或删除减速尾段。`after_two_doors_04`两次最终窗口各42个样本，约1.46秒，移除后到达窗口角速度最大约0.01066rad/s。动作结束时仍在减速并不被提前判为已停稳。

## 保留用户场景的手动重启

旧进程缓存了启动时加载的行为树，更新文件不等于现有动作自动切换。用户在原启动终端Ctrl+C结束旧导航后，可以运行：

```bash
cd /home/jiazhengfu/Projects/STM32-CAN-SmartCar
bash docs/evidence/nav2-blocked-passages-20261019/user_session/restart_navigation.bash
```

该脚本使用本轮只读快照生成的`resume_world.sdf`，保留球体、方块及原有模型，机器人从快照世界位姿约(-0.473147,2.94194,-0.119911rad)重新启动，初始AMCL匹配。它只启动导航，不发送目标。已有独立RViz时给脚本加参数`false`；原RViz若随旧launch关闭则保持默认。旧仿真未退出时，原有重复接口检查仍会拒绝启动。

恢复模板经过项目`load_world`检查，脚本通过`bash -n`与`--show-args`检查；没有自动打开用户窗口来替用户复测恢复界面。快照是接手时状态，未覆盖原office_loop或地图文件，重启后运行期障碍记忆重新建立。

自动复核使用显式隔离入口，输出目录必须全新：

```bash
python3 ros2_ws/tools/verify_replanning.py --case two_doors --reopen \
  --domain-id 94 --goal-timeout 240 --output "$PWD/ros2_ws/verification_runs/two_doors_next_01"
python3 ros2_ws/tools/verify_replanning.py --case two_doors --through-poses \
  --domain-id 92 --output "$PWD/ros2_ws/verification_runs/through_next_01"
```

`config/`保存每轮实际配置；后续轮次也保存完整验收器快照，初始基线使用报告中的验收器源码哈希和明确的旧BT覆盖记录追溯。`result.json`记录实际结果与原始哈希。`SHA256.json`为本轮归档校验；压缩归档及未压缩原件位置见`compression.json`。旧报告不改写为新结论；每轮全部路径、扫描、全局图和CSV可复核。

JSONL已无损归档为`.jsonl.gz`，解压字节与各轮`result.json`中的原名/原始哈希逐一核对；报告保持原样。未压缩原件仍保留在忽略的`ros2_ws/verification_runs/nav2-blocked-passages-20261019-raw/<运行>/`，CSV直接保留于各证据目录。扫描无穷远值保留为Python JSON的`Infinity`，不当作有限距离。
